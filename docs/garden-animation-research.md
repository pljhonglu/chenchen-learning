# 首页小兔与小树动画调研

> 本文记录最初的兔子浇水方案。多轮视觉反馈后，表现方向已重新评估，请优先阅读 [首页养成表现：同类产品与实现方案](garden-growth-directions.md)。本文的业务隔离与生命周期分析仍可参考，兔子动作设计不再作为推荐方向。

调研日期：2026-10-04。基于 `feat/go-child-friendly-learning` 分支、提交 `5df915e`。

建议采用 **GSAP 时间线 + 分层绘本素材 + 独立场景控制器**。保留奶油色、水彩和纸纹风格，把小兔的表情、耳朵、身体，以及树的枝叶、花果做成可独立控制的部件。动画库负责协调动作；自然的角色表现仍取决于素材、支点和动作设计。只把现有整张 PNG 的 CSS 动画换成 JavaScript，不足以明显改善观感。

如果后续要长期制作有骨骼变形、丰富表情和多动作切换的小兔，Rive 是值得采用的另一条路线；当前仓库没有相关动画源文件，需先完成资源制作与导出流程。本轮完成代码与素材审阅、原有前端的隔离浏览器复现、官方资料调研，尚未实现新动画。

**当前项目和动画结构**

项目采用 Go + SQLite 后端，前端为原生 HTML、CSS、JavaScript，通过 script 标签加载模块，无 React 或前端打包流水线。动画可以直接接入现有静态资源结构。

**观感问题和已复现的问题**

1. **小兔只有一个姿势。** `companions.png` 内小兔是一整张位图；呼吸是整张图缩放，跳跃是整张图上移 7px 并旋转。眼睛、耳朵、头、手臂没有独立动作，缺少起跳前的下蹲、耳朵的滞后和落地缓冲。
2. **成长实际是换图。** 服务端成功后立即渲染新阶段，`g-tree-grow` 将新图片从 0.92 倍放大到 1.025 倍再恢复。旧阶段没有留在场景中，叶片、枝条也没有单独出现，因此缺乏“同一棵树长出新东西”的连续感。
3. **树的动作相互覆盖。** `g-just-grown .g-tree` 与 `g-just-watered .g-tree` 都设置 `animation`，成长规则排在后面，替代了浇水回应。整棵树连同根部一起旋转，也容易产生贴纸感。
4. **浇水缺少空间联系。** 小兔在左、水壶在右，水壶自行转动；水滴容器使用固定的 right/bottom 数值，没有绑定壶嘴和树根。桌面画面中壶离树根很远，现有水滴的运动没有明确抵达树根。应建立统一场景坐标及壶嘴、树根锚点。
5. **每日第 3 次浇水会关闭主要动作。已复现。** 成功后 `wateredToday >= 3` 立即加上 `g-resting`，CSS 将树、兔子、水壶的 animation 设为 none，但水滴和礼物仍播放。以累计 23 滴、今日已浇 2 次为例，第 24 滴成长时观察到树、兔子、水壶均为 none，水滴为 `g-drop-fall`，礼物为 `g-gift-appear`。正确节奏应是播完本次成功反馈，再进入安静状态。
6. **连续浇水会提前清除后一次动画。已复现。** `watering` 只覆盖网络请求，成功后立即解锁；每次成功又建立独立的 2600ms 清理定时器。两次点击相隔约 1 秒，第二次播放约 1.75 秒时水滴及动作 class 已被第一次的定时器清除，早于第二次应有的 2.6 秒。
7. **整体重绘不利于连续表演。** 请求前后均调用 `paintHome()`，删除并重建场景 DOM。后续即使引入动画库，也需要解决元素被替换、播放被打断和清理回调串到下一次动作的问题。当前也没有显式的页面隐藏处理。

树图集另有维护问题：实际行距不等分，`treeStyle()` 已为第三、四行手工修正裁切和宽高比。这些图片适合作为当前阶段的静态展示，不适合作为自然生长的连续动画帧。

**动画库比较**

下表的适配结论是结合项目结构和所需动作的工程判断，不是性能跑分。

| 方案 | 能解决什么 | 本项目需要补的工作 | 判断 |
| --- | --- | --- | --- |
| GSAP + 分层 PNG/WebP/SVG | 用时间线组织先后、重叠和缓动，统一控制播放和清理 | 分层素材、支点、场景控制器 | 当前首选，能直接接入原生 JS，动画逻辑易于在仓库维护 |
| Rive | 状态机、骨骼、位图网格变形，适合精细角色动作 | 制作可编辑源文件及 `.riv`，接入运行时/WASM，验证所用功能对应的渲染器 | 适合把小兔发展成长期维护的动画角色 |
| Lottie / dotLottie | 播放预先制作的动画，适合浇水、礼物等固定片段；dotLottie 也有状态机 | 制作匹配绘本风格的资源，维护阶段与片段切换 | 可以用，但当前复杂度主要在资源制作，单加播放器帮助有限 |
| Anime.js | 同样提供时间线，适合代码驱动的 DOM/SVG 动画 | 与 GSAP 相近的分层和场景编排工作 | 可行替代，若优先 MIT 许可可选；没有必要同时引入两套时间线库 |

GSAP 的 Timeline 支持动画、回调、标签与嵌套序列，适合统一编排这段场景；可用普通 script 接入。`context()` 提供作用域和回收，`matchMedia()` 可按屏幕条件与减少动态效果偏好调整。来源：[Timeline](https://gsap.com/docs/v3/GSAP/Timeline/)、[安装](https://gsap.com/docs/v3/Installation/)、[context](https://gsap.com/docs/v3/GSAP/gsap.context()/)、[matchMedia](https://gsap.com/docs/v3/GSAP/gsap.matchMedia()/)。

GSAP 当前采用自有 Standard No Charge 许可，并非 MIT；官方明确一般商业项目也可免费使用，须保留声明并遵守其条款。本项目计划只使用核心时间线，实施时固定实际选用版本并随库保存许可。来源：[GSAP 许可](https://gsap.com/community/standard-license/)。

Rive 支持用骨骼控制部件、用网格让位图局部自然变形，因此可以沿用水彩质感，不必改成扁平矢量。它的 Web 接入为 JavaScript/WASM，并能自行托管 WASM；具体用 Canvas 还是 WebGL2，应按素材用到的功能核对兼容性。来源：[骨骼](https://rive.app/docs/editor/manipulating-shapes/bones)、[网格](https://rive.app/docs/editor/manipulating-shapes/meshes)、[状态机](https://rive.app/docs/editor/state-machine/state-machine)、[Web 运行时](https://rive.app/docs/runtimes/web/web-js)、[托管 WASM](https://rive.app/docs/runtimes/web/preloading-wasm)。

Rive 的费用要区分编辑/导出与运行时。调研当天实时打开的官方价格页显示：Free 可导出带 Rive 启动画面的 `.riv`；Cadet 可导出无启动画面的文件，页面列价 $9/席位/月。搜索摘要仍能看到“免费版不能导出”的旧信息，这里以实时页面为准；正式选用时再次确认方案与计费周期。来源：[Rive 价格页](https://www.rive.app/pricing)。

Lottie 常见工作流是制作动画后导出 JSON，由 Web 播放器渲染；不能因此认定它“只能播放、不能交互”：dotLottie Web 已支持加载状态机并由应用输入驱动切换。这里未将其列为首选，是因为本项目仍需定制角色和连续生长资源。来源：[lottie-web 官方仓库](https://github.com/airbnb/lottie-web)、[dotLottie 状态机](https://docs.lottiefiles.com/en/runtimes/distributions/js/v0.x/state-machines)。Anime.js 的能力与许可见[时间线文档](https://animejs.com/documentation/timeline/)及[许可文件](https://github.com/juliangarnier/anime/blob/master/LICENSE.md)。

**建议的动作设计**

保留温暖、安静的绘本气质，让短暂动作有明确原因和结果。以下时间是设计起点，需根据预览调整，不是已经实现的效果。

| 场景 | 动作设计 | 建议时长 |
| --- | --- | --- |
| 进入首页 | 小兔一次眨眼、轻轻点头，耳朵稍晚恢复；树叶轻摆后停下 | 约 1.5–2 秒 |
| 请求等待 | 按钮显示等待，角色可有轻微准备动作；不提前展示水已浇下或树已长大 | 随请求完成 |
| 普通浇水 | 小兔看向树、带动水壶靠近，水壶倾斜，水流落到树根；土地微湿，叶子由近及远回应；小兔点头 | 成功后约 2.8–3.2 秒 |
| 12 滴里程碑 | 先完成浇水；固定根部，新叶展开或枝条延伸；花苞、花、果按阶段出现；小兔下蹲后小跳一次，耳朵跟随；最后礼物出现 | 整段约 4–5 秒 |
| 完成每日第 3 次 | 完整播完这次浇水/成长，再安静落回休息姿态 | 不额外循环 |
| 减少动态效果 | 直接更新最终树形、计数和成功文字，礼物静态呈现 | 即时 |

例如里程碑的一段时间线可从“准备 0–0.4s → 倾壶与水流 0.4–1.7s → 吸水回应 1.5–2.1s → 生长 2.0–3.5s → 小兔庆祝与礼物 3.4–4.6s”起步。水流、枝叶、小兔之间允许少量重叠，礼物应在关键树形变化之后出现，避免先遮住树。

**素材制作要求**

- 小兔：身体/背带裤、头、左右耳、眼睛或上下眼睑、左右手臂、脚、尾巴、地面阴影分别制作；确定颈部、耳根、肩膀等支点。耳朵做滞后和回弹，阴影随起跳收缩，身体轻微压缩后起跳。眨眼需要独立眼部素材，整张图上的缩放无法替代。
- 小兔若要真正拿起水壶，需有对应手臂姿势、握持锚点和前后遮挡关系。不能只把现有水壶平移到兔子旁就当作完成握持动画。
- 树：保持根部坐标与主干轮廓的连续性，分出主干、侧枝、若干叶簇、嫩叶、花苞、花、果、来访动物和鸟窝。16 个业务阶段映射到这些部件的显隐和成熟状态，成年后的四阶段循环仍沿用现有规则。
- 枝叶从连接点展开，主干可以用蒙版逐步显现；水流用轻量 SVG 路径/少量水滴，水壶和水流起点共用锚点。避免给整棵树做大幅旋转或橡皮般拉伸。
- 一套 SVG viewBox 可作为统一场景坐标系，内部放置绘本位图图层和 SVG 水流。桌面、平板、手机整体缩放或调整场景布局，壶嘴与水滴、树根的关系不会因分别写像素位置而错开。
- 素材必须补齐被遮挡的连接处，统一透明边缘、比例、光照和支点；保留可编辑源文件。当前 PNG 可以作为风格参考和静态后备，但从整图裁出耳朵或枝叶往往会露出缺口，不能承诺无损自动拆分。

资源制作是本次质量提升的主要工作之一。若先保留旧树图集，只做根部对齐的双层交叉淡化，可以改善突变，但这只是过渡方案，不等价于枝叶真实生长。

**建议的代码落点与状态管理**

新增 `public/garden-scene.js`，作为场景控制器；新增 `public/garden-scene.css` 管理分层排布；选定 GSAP 版本本地保存到 `public/vendor/`，新素材保存到 `public/images/garden/`。同步更新 vendor 许可和素材说明。

控制器建议暴露 `mount(root, snapshot)`、`setSnapshot(snapshot)`、`playWater(receipt, before, after)`、`setReducedMotion(value)`、`destroy()` 等接口。这是拟定接口，仓库目前尚无这些实现。

`garden.js` 继续负责真实请求、幂等 ID、余额、每日额度和礼物记录。服务端成功后立即接收权威状态，再让视觉模块表现这次结果。动画结束回调只用于视觉收尾，不能承担扣水、成长或发礼物，也不能因跳过动画而漏存进度。

保留一份仅供过渡的旧树形，收到成功结果后从旧阶段表现到新阶段。按请求 ID/服务端浇水记录识别本次事件，避免把重试或跨设备同步误认成多次成长。重载页面直接显示服务端最终树形；请求在后台完成或返回新页面时优先同步最终状态，不补播一串过期庆祝。

建议单一视觉状态流程为 `idle → waiting → pouring → growing（仅里程碑）→ celebrating（仅里程碑）→ idle/resting`。等待失败返回可重试状态；视图离开、页面隐藏、减少动态效果变化均有显式处理。不要仅以 `wateredToday >= 3` 覆盖正在播放的成功反馈。

保留场景 DOM，仅更新标题、计数、按钮和局部图层；若必须整体重建，先销毁控制器。一次只允许一个浇水时间线，播放期间禁止再次发起浇水；导航依然可用。用控制器和事件标识取消旧回调，消除前次定时器影响后次的情况。

离开页面清理时间线、监听器和临时图层；页面隐藏时暂停或直接收束到最终状态，回来后不补播过期片段。JS 主动监听 `prefers-reduced-motion`，不能依赖 CSS 的 `animation:none` 去停止 GSAP。动画库或素材加载失败时应显示静态树形和结果文字，学习与保存继续可用。

**实施顺序与验收**

1. 先做独立预览：小兔眨眼/耳朵回弹、普通浇水、0→1 阶段长叶各一段。使用模拟状态，验证分层绘本风格、握壶动作和树根锚点的质量。
2. 完成场景控制器和成功反馈接入，处理第 3 次浇水、连续点击、导航清理、减少动态效果；将同一套动作扩展到全部 16 阶段。
3. 验证成年循环 15→12、跨日、网络失败后相同 ID 重试、后台完成、同步变化、素材失败。重新跑现有花园测试并补充有意义的控制器/浏览器回归。
4. 在 390px 手机、820px 平板、桌面检查壶嘴/树根对齐、最大树冠、兔耳及标题/礼物遮挡；再在实际手机 Safari/Chrome 检查流畅度、耗电与后台停止。目标是动作期间尽量保持 60fps，安静后无持续无意义的动画循环；实际指标需实现后测量。
5. 压缩和预载实际需要的资源，对比改造前后首页资源大小、解码耗时与帧耗时。库体积应连同位图、WASM（如果选 Rive）和缓存策略一起评价，不用不同口径的宣传数字代替实测。
